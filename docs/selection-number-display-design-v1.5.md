### 1. 목적과 범위

본 설계는 기존 B-1 Selection Number의 영속성을 보존하면서 사용자 화면에 필요한 경우에만 객체 선택 번호를 표시한다.

내부 번호를 변경하거나 새로운 번호 체계를 도입하지 않는다.

대상 구별이 필요 없는 경우 자연스러운 이름을 사용하고, 실제 객체를 구별해야 하는 경우 저장된 번호를 사용한다.

이 변경에서 해결해야 하는 문제는 네 가지다.

1. 불필요한 번호가 화면과 게임 서술에 표시되는 문제
2. 실제 이름과 번호의 충돌로 잘못된 객체가 선택될 가능성
3. 표시 이름과 텍스트 명령과 웹 실행 참조의 혼용
4. B-1 영속 번호와 기존 Legacy 인덱스의 불일치

#### 1.1 변경하지 않는 사항

- B-1 Selection Number 저장 구조
- 기존 Scope 및 안정 그룹
- 번호 순차 할당
- 결번 및 빈 그룹 초기화 정책
- 기존 번호의 임의 재할당 금지
- 실제 객체 이름의 변경 금지
- 일반 입력의 정식 이름 우선 정책
- 기존 DEFAULT / INDEX / ALL 기본 계약
- Player·Party·Legacy 스택의 비 B-1 번호 정책
- 기존 게임 효과와 도메인 Service
- 기존 TargetReference의 기본 구조
- 플레이 DB 및 저장 데이터

DB 마이그레이션은 수행하지 않는다.

### 2. 핵심 개념

동일 객체에 서로 다른 목적의 표현을 사용한다.

| 개념 | 정의 |
|---|---|
| World Name | 객체의 실제 세계 표현 이름. 예: `obj.key` |
| Canonical Selection Name | B-1의 정식 선택 이름. `SelectionRecord.name` |
| Alias | 기존 선택 별칭 |
| Selection Number | 저장된 B-1 영속 번호 |
| Display Label | 플레이어에게 보여 주는 조건부 번호 포함 이름 |
| Selection Text | 특정 텍스트 명령에서 대상을 정확히 선택하는 구문 |
| TargetReference | `{kind, identity, scope_id}` 안정 참조 |

#### 2.1 정식 선택 이름

정확한 선택의 기준은 `SelectionRecord.name`이다.

World Name과 Canonical Selection Name이 항상 같다고 가정하지 않는다.

예를 들어 Corpse의 정식 선택 이름은 `시체`, Door의 정식 선택 이름은 `문`이다.

객체의 실제 `key`나 기존 별칭이 다르더라도 인용 번호 선택은 B-1의 정식 선택 이름을 기준으로 한다.

#### 2.2 실행 불변식

- **I01 — 영속성:** 번호 표시 여부는 저장된 번호를 변경하지 않는다.
- **I02 — 선택 정확성:** B-1 명시 번호는 배열 인덱스가 아니라 저장된 번호다.
- **I03 — 실행 안정성:** 구조화 웹 요청은 생성 당시의 TargetReference를 기준으로 실행한다.
- **I04 — 표시 독립성:** Display Label이 바뀌어도 TargetReference는 변경되지 않는다.
- **I05 — Scope 독립성:** 서로 다른 Scope의 번호를 합치거나 재번호하지 않는다.
- **I06 — 기존 명령 보존:** 번호를 생략했을 때의 DEFAULT 선택과 기존 ALL 동작을 의도 없이 변경하지 않는다.
- **I07 — Fail-closed:** 선택 결과가 유일하지 않거나 참조가 유효하지 않으면 임의 대상을 실행하지 않는다.
- **I08 — 정보 보호:** 비공개 객체나 권한이 없는 대상의 존재를 표시·오류·번호 계산을 통해 노출하지 않는다.

### 3. 조건부 번호 표시

#### 3.1 기본 규칙

같은 공개 표시 문맥에서 동일한 정식 선택 이름을 가진 대상이 하나라면 번호를 생략한다. 둘 이상이면 실제 영속 번호를 표시한다.

| 실제 대상 | 표시 |
|---|---|
| 갈퀴사냥룡 번호 1 하나 | 갈퀴사냥룡 |
| 갈퀴사냥룡 번호 7 하나 | 갈퀴사냥룡 |
| 갈퀴사냥룡 번호 2와 4 | 갈퀴사냥룡 2 / 갈퀴사냥룡 4 |
| 번호 2 삭제 후 번호 4만 남음 | 갈퀴사냥룡 |

다른 객체의 삭제나 비공개 상태 때문에 기존 실물의 영속 번호를 바꾸지 않는다.

#### 3.2 공개 표시 문맥

Room에 대해서는 같은 플레이어, Room, 관찰 시각을 기준으로 공개 표시 Snapshot을 생성한다.

표시 계산에는 관찰 가능한 대상만 사용한다.

다음 상태는 번호 표시 여부의 직접적인 판단 기준이 아니다.

- 공격 가능 여부
- 대화 가능 여부
- 시설 조작 가능 여부
- 전투 참여 여부
- Action 제공 여부

동일한 공개 Room 대상은 화면 영역에 관계없이 같은 Display Label을 사용한다.

단, 소지품, 보관함, 시체 내부 전리품 등 별도 Scope는 각각의 실제 선택 문맥에서 계산한다.

#### 3.3 이름 충돌

표시 정책은 동일 이름의 개수만 검사해서는 안 된다.

| 객체 | 정식 선택 이름 | 영속 번호 |
|---|---|---|
| A | 장치 | 2 |
| B | 장치 | 4 |
| C | 장치 2 | 1 |

단순한 표시 결과는 A와 C가 모두 `장치 2`가 되는 문제를 만든다.

수정된 출력은 다음과 같다.

- `"장치" 2`
- `장치 4`
- `장치 2`

이때 A의 인용 표기는 실제 번호와 정식 이름을 정확하게 지정한다.

#### 3.4 예약 구문 형태의 실제 이름

정식 선택 이름 자체가 유효한 인용 번호 구문처럼 생겼다면, 단일 객체여도 원문 표시가 선택 구문으로 오인될 수 있다.

따라서 해당 경우에는 정확한 인용 번호 표기를 사용한다.

정식 선택 이름: `"장치" 2`\
영속 번호: 5\
정확한 표기: `"\"장치\" 2" 5`

이렇게 해야 다른 객체의 인용 번호 선택과 구별할 수 있다.

#### 3.5 표시 충돌 해소 알고리즘

1. 공개 대상의 Canonical Selection Name을 수집한다.
2. 기존 일반 선택의 정규화 기준으로 이름 충돌 가능성을 계산한다.
3. 구별이 필요한 동일 이름 대상에 저장 번호를 붙인다.
4. 생성된 표시가 다른 객체의 실제 이름이나 표시와 충돌하는지 검사한다.
5. 충돌하는 번호 선택 표기를 정확한 인용 표기로 변경한다.
6. 예약 구문처럼 보이는 실제 이름도 인용 표기로 변경한다.
7. 최종 공개 표시의 중복과 선택 가능성을 다시 검사한다.

인용 표기를 단순히 중첩해 다른 번호를 가진 대상을 선택하도록 변형해서는 안 된다.

각 객체의 인용 표기는 반드시 자신의 정식 이름과 영속 번호를 가리킨다.

동일한 인용 문자열이 서로 다른 Scope에서 각각 유효한 경우에는 Scope 문맥을 별도로 제공한다.

하나의 텍스트 명령으로 유일한 대상을 지정할 수 없다면 정확한 실행 문자열을 생성하지 않는다.

#### 3.6 자연어 출력

일반 세계 서술에서는 자연스러운 이름을 우선한다.

`갈퀴사냥룡이 날카로운 발톱으로 당신을 할퀴었다!`

복수의 동일 이름 객체 중 정확한 실물 식별이 필요한 경우에는 선택 번호를 사용한다.

영속 번호를 자연어 서수로 취급하지 않는다.

특히 `시체 4`는 네 번째 시체를 뜻하지 않는다.

### 4. 텍스트 선택 문법

#### 4.1 일반 입력

기존 문법을 유지한다.

- `이름`
- `이름 번호`
- `이름 모두`

정식 이름 우선, 별칭, 기존 기본 선택 정책을 보존한다.

#### 4.2 인용 번호 문법

B-1 대상에 한해 다음 문법을 추가한다.

`"정식 선택 이름" 번호`

정확한 인용 선택은 다음 조건을 따른다.

- ASCII 큰따옴표 사용
- 닫는 큰따옴표 뒤 공백과 번호
- 번호는 1 이상의 정규 십진수
- 선행 0을 허용하지 않음
- 실제 B-1 번호 저장 범위를 넘는 값 거절
- 인용 이름의 큰따옴표와 역슬래시 이스케이프 지원
- 인용 이름 내부의 공백을 원문 그대로 보존
- 그 밖의 임의 이스케이프 변환 금지

입력 길이와 숫자 파싱에도 명시적인 상한을 적용한다.

#### 4.3 정확한 일치 기준

인용 번호 선택은 다음 값으로 실물을 찾는다.

`Canonical Selection Name + Selection Number + Role/Scope`

이름 비교는 이스케이프 해제 후 정확한 문자열 일치다.

다음 변환을 수행하지 않는다.

- 기존 `normalized()` 적용
- 공백 제거
- 구분 문자 제거
- casefold
- Unicode 정규화
- 별칭 확장

동일한 조건으로 두 개 이상의 실물이 선택되면 거절한다.

#### 4.4 일반 입력과 인용 입력의 우선순위

B-1 대상 선택 문맥에서 다음 순서를 적용한다.

1. 완전하고 유효한 인용 번호 구문 판정
2. 유효하면 정확한 인용 선택
3. 해당 구문이 아니면 기존 일반 정식 이름 조회
4. 기존 명시 번호·별칭 해석
5. 기존 DEFAULT / ALL 정책

유효한 인용 번호 구문은 B-1 선택 문맥의 예약 구문이다.

불완전하거나 유효하지 않은 인용 형태는 기존 실제 이름 조회 가능성을 확인한 후 오류를 처리한다.

유효하지 않은 인용 번호를 다른 객체의 번호로 추측해서는 안 된다.

#### 4.5 비 B-1 대상과의 경계

새로운 인용 번호 문법은 B-1 대상에 한정한다.

Player, Party 및 Legacy 스택 등에는 새 번호 문법을 자동 적용하지 않는다.

공통 파서는 인용 구문을 인식할 수 있지만, 실제 적용 가능 여부는 해당 명령의 대상 종류와 Role 계약이 결정한다.

`봐`처럼 여러 종류의 대상을 조회하는 명령은 유효한 인용 B-1 선택 구문을 기존 Door·Object·Item 이름 우선순위에 의해 다른 대상으로 재해석하지 않는다.

기존 일반 입력은 원래의 조회 우선순위를 유지한다.

유효한 인용 구문과 동일한 원문을 가진 비 B-1 실제 이름이 혼합 명령에서 충돌하는 특수 사례는 예약 문법의 제한으로 명시한다. 기존 비 B-1 전용 명령의 의미를 변경하지 않는다.

#### 4.6 관계 조사

다음 입력을 지원한다.

- `"장치에서 발견한 부품" 2 조사`
- `"시체" 2에서 회수부품 모두 가져`
- `"윤대장" 2에게 안녕 말`

관계 조사는 인용 영역 바깥에서만 분리한다.

공백으로 분할하거나 인용 영역 내부의 `에게`, `에서`를 관계 조사로 오인하지 않는다.

기존 복합 명령 문법과 Action Variant는 필요한 최소 범위에서만 확장한다.

### 5. 구조화 선택자와 Resolver

#### 5.1 공통 선택 표현

파서는 일반 선택과 인용 정확 선택을 구별할 수 있는 내부 구조를 사용한다.

최소한 다음 정보를 보존한다.

- 선택 이름
- DEFAULT / INDEX / ALL
- 명시 번호
- 일반 선택 또는 인용 정확 선택 여부
- 원본 이름의 이스케이프 해제 결과

새로운 영속 모델이나 명령 DSL을 도입하지 않는다.

#### 5.2 선택 정보 손실 금지

파싱 이후에는 인용 선택자를 일반 `이름 번호` 문자열로 바꿔 정확 선택 정보를 버리지 않는다.

다음 경로에서 공통 선택 표현을 유지한다.

- `targets.resolve()`
- `actions.resolver.select_role()`
- `actions.resolver.dispatch_text()`
- `loot_parts()` / `parse_loot()`
- `loot_resolution.resolve()`
- NPC 명시 대상 선택
- Door 선택
- Native ItemEntity 선택

필요하면 기존 선택 함수가 구조화된 선택자를 직접 받을 수 있도록 확장한다.

#### 5.3 B-1 정확 선택

B-1 명시 번호는 반드시 저장된 Selection Number와 비교한다.

후보 배열의 위치를 사용하지 않는다.

조회에 사용하는 번호 행은 다음 정보를 현재 실물과 대조한다.

- ReferenceKind
- Identity
- Scope
- 안정 Group
- Canonical Selection Name
- 저장 Number

불일치하거나 번호가 누락된 대상은 정확 선택을 실패로 처리한다.

#### 5.4 기존 기본 정책

번호 없는 일반 입력은 기존 기본 선택 계약을 유지한다.

`FIRST_LEGACY_ORDER`를 명시적 영속 번호 선택과 혼동하지 않는다.

`REQUIRE_UNIQUE`는 후보가 여러 개면 기존처럼 거절한다.

`ALL`은 기존 범위와 권한 제한을 유지한다.

인용 정확 선택을 이유로 별칭이나 DEFAULT 정책 전체를 재설계하지 않는다.

---

### 6. Native ItemEntity와 Legacy 경계

#### 6.1 실제 전환 범위

B-1 ItemEntity와 Legacy 스택을 구분한다.

현재 `equipment_service.resolve_item()`과 `item_transfer_native.transfer()`에는 Native ItemEntity를 대상으로 후보 배열 순서를 사용하는 명시 번호 선택 경로가 존재한다.

이러한 경로는 명시 번호를 B-1 영속 번호로 해석하도록 전환해야 한다.

#### 6.2 기존 동작 보존

명시 번호 해석만 영속 번호로 전환한다.

기존 다음 기능은 유지한다.

- 번호 없는 기본 선택
- 기존 후보 순서 및 기본 선택 정책
- `모두`
- 스택 수량 처리
- 일부 수량 분리
- 장비 장착·해제
- 보관·회수·전달
- 소유권 및 이동 검증
- 아이템 병합과 UUID 생명주기

배열 위치와 영속 번호가 다를 때 정확한 실물을 선택하는 회귀 테스트가 필수다.

#### 6.3 Legacy 경계

비 B-1 Legacy 스택 선택에는 기존 정책을 적용한다.

`targets.stack_selector()`와 `targets.item_selector()`의 Legacy 역할을 임의로 변경하지 않는다.

Native ItemEntity와 Legacy Profile Inventory가 공존할 수 있는 경로에서는 실제 선택 대상의 데이터 종류를 먼저 판별한다.

### 7. 텍스트 명령 생성

#### 7.1 Display Label과 분리

Display Label을 직접 실행 문자열로 사용하지 않는다.

텍스트 명령 생성기는 해당 명령의 실제 Role과 Scope를 사용하여 정확한 대상 선택 문자열을 만든다.

일반 `이름 번호`로 유일하게 선택할 수 있다면 이를 사용한다.

정식 이름 우선 규칙 때문에 충돌하면 `"이름" 번호`를 사용한다.

두 방식 모두 유일한 대상을 보장하지 못하면 실행 가능한 문자열을 생성하지 않는다.

#### 7.2 복합 명령

Source와 Subject가 별도 Scope를 사용하는 경우 전체 명령 단위로 정확성을 검사한다.

예를 들어 다음 요소를 각각 선택하고 조합한다.

- Corpse Source
- 해당 Source 내부 Loot
- 전리품의 수량 또는 ALL 조건

전체 명령이 기존 전리품 보호·권리·Snapshot 계약을 보존해야 한다.

#### 7.3 왕복 검증

생성한 명령은 해당 Role 및 Scope에서 재해석했을 때 원래 대상을 정확하게 선택해야 한다.

`resolve(parse(selection_text), context) == original_reference`

복합 명령은 Source와 Subject의 전체 참조 집합을 기준으로 검증한다.

이 검증은 명령을 생성한 시점의 정확성에 대한 계약이다.

시간이 지난 일반 텍스트 명령의 영속 참조를 보장하지 않는다.

### 8. 웹 실행 안정성

#### 8.1 구조화 요청 우선

대상을 지정하는 웹 버튼은 기존 Typed Action + TargetReference를 우선 사용한다.

기존 버튼의 Display Label은 표현에만 사용한다.

번호나 문자열로 대상 Identity를 재구성하지 않는다.

#### 8.2 대상 관찰

현재 `global.look`은 문자열 `query`를 사용하는 전역 Action이며 대상 Role을 가지고 있지 않다.

따라서 기존 `global.look`에 단순히 TargetReference를 덧붙이는 방식은 허용하지 않는다.

대상 참조를 명시적으로 받는 제한된 관찰 Action 또는 서버 어댑터를 제공한다.

이 경로는 다음을 수행한다.

1. 원래 TargetReference를 수신한다.
2. 현재 실물·Scope·권한을 검증한다.
3. 정확히 해당 실물을 대상으로 기존 관찰 로직을 실행한다.
4. 다른 이름이나 번호로 다시 선택하지 않는다.

기존 텍스트 `봐` 명령의 문법과 조회 우선순위는 유지한다.

#### 8.3 NPC 대화

기존 대화 화제 버튼에서 사용하는 서버 발급 `pz_dialogue` 토큰은 그대로 재사용한다.

해당 토큰은 NPC Identity, Intent 및 Session에 연결된다.

새로운 일반 `말 걸기` 버튼은 원래 NPC 참조를 사용하는 안전한 실행 경로로 전환한다.

표시 Snapshot 조회 중 새로운 대화 토큰을 발급하지 않는다.

대화 토큰 발급과 실행은 기존 대화 생명주기 계약을 따른다.

#### 8.4 기타 버튼

다음 대상 지정 버튼을 감사한다.

- Enemy 공격 및 관찰
- Duel
- Corpse 관찰 및 Loot 회수
- NPC 대화 및 시설 조작
- Container 관찰
- Door 관찰·조작
- ItemEntity 장비·사용·보관
- 기타 B-1 대상 지정 문자열 버튼

이미 안전한 Typed Action을 가진 버튼은 기존 경로를 재사용한다.

구조화 Action으로 전환할 수 없는 대상 지정 기능은 서버 측 안정 참조 검증을 포함한 제한된 어댑터를 사용한다.

#### 8.5 검증 후 문자열 재선택 금지

다음 방식은 허용하지 않는다.

`TargetReference 검증 → 기존 이름 문자열 생성 → 일반 명령 실행`

이는 검증 이후 다른 객체를 선택할 가능성을 남긴다.

실제 실행에는 검증된 실물 참조를 직접 전달해야 한다.

대상 검증과 도메인 효과는 기존 잠금·트랜잭션 계약을 따른다.

#### 8.6 오래된 버튼

버튼 생성 후 객체가 삭제되거나 이동하거나 번호가 재사용되어도 원래 TargetReference만 검증한다.

다른 객체로 재선택하지 않는다.

Enemy·Duel처럼 별도 생명주기나 세대 검증이 필요한 경로는 기존 generation/lifecycle 조건도 보존한다.

잘못된 참조 요청으로 다른 객체에 발생하는 게임 효과는 0회여야 한다.

#### 8.7 구버전 클라이언트

구버전 브라우저가 문자열 버튼을 일반 명령처럼 전송하는 경우, 서버에서 직접 타이핑한 명령과 구별할 수 없는 한 안정 버튼의 대상 고정을 보장할 수 없다.

따라서 다음 호환 경계를 둔다.

- 새 UI에서 대상 지정 버튼은 구조화 요청 사용
- 변경 전 웹 클라이언트에는 갱신·재접속을 요구
- 필요하면 기존 클라이언트 버전 검사 또는 갱신 정책 사용
- 직접 입력한 일반 명령은 기존 현재 대상 선택 계약 유지

프로토콜상 구별할 수 없는 구형 요청까지 안전하다고 선언하지 않는다.

### 9. 표시 Snapshot

#### 9.1 생성 계약

기존 Room 생명주기 정합화가 필요한 경우 해당 처리가 끝난 뒤 공개 표시 Snapshot을 생성한다.

동일 요청에서는 일관된 관찰 시각과 공개 대상 집합을 사용한다.

표시 계산 자체는 읽기 전용이다.

번호 생성, 상태 변경, 신규 토큰 발급, 보상 확정 등의 효과를 수행하지 않는다.

#### 9.2 재사용

Room 공개 Snapshot을 다음 영역에 공유한다.

- 주변 대상 목록
- NPC 및 시설
- Enemy
- Corpse
- Door
- Duel 대상 표시
- 같은 공개 문맥의 Action Label

Inventory, Storage, Inside ItemEntity, Loot 등은 각자의 Scope에 적합한 별도 표시 문맥을 사용한다.

#### 9.3 기존 API 보존

`selection_numbers.api.label()`은 기존 저수준 번호 포함 표기 API로 유지한다.

새 조건부 표시 정책은 별도 공통 계층에서 제공한다.

Legacy Player·Party 등의 기존 `labels()` 동작을 무조건 새 정책으로 바꾸지 않는다.

B-1 표시에 사용되는 호출 지점만 명시적으로 새 API로 전환한다.

#### 9.4 번호 누락

번호 누락 시 임시 번호를 생성하지 않는다.

실제 세계 이름은 안전한 자연어 서술에 사용할 수 있다.

정확한 번호 선택 또는 텍스트 명령을 보장할 수 없는 경우 이를 제공하지 않는다.

구조화 Action도 필요한 번호 및 대상 무결성 조건을 만족할 때에만 제공한다.

번호 누락은 검증 가능한 결함으로 기록한다.

### 10. 보안 및 권한

기존 Gateway와 도메인 Service를 모든 실행의 최종 검증 경계로 유지한다.

다음 요소를 실행 시점에 재검증한다.

- Session·Account·Puppet 제어권
- TargetReference의 현재 Identity와 Scope
- Room 및 관찰 가능성
- Action 제공 상태
- Capability
- 소유권
- Storage 접근 권한
- Loot 보호와 배정
- 전투·Duel 상태
- 수량·비용·기타 실행 조건

숨겨진 객체는 표시 충돌 계산에 사용하지 않는다.

비공개 대상의 존재 여부를 오류 메시지에서 구별할 수 없도록 한다.

실패한 대상 요청으로 다른 객체에 대한 도메인 효과가 발생해서는 안 된다.

### 11. 성능 계약

#### 11.1 조회 구조

동일한 표시 문맥의 번호는 일괄 조회한다.

개별 객체마다 `number_for()`를 반복하지 않는다.

Room의 B-1 번호는 가능한 한 하나의 배치 조회로 획득한다.

Inventory 및 여러 Source Scope도 범위별 개별 객체 조회 대신 Scope 집합 기반 배치 조회를 우선한다.

이미 수집된 Selection Record와 번호는 같은 표시 Snapshot 안에서 재사용한다.

#### 11.2 검증 데이터

1개, 10개, 100개 대상에 대해 동일 데이터와 환경에서 변경 전후를 비교한다.

대표 측정 대상은 다음과 같다.

- Room 공개 상태 응답
- Inventory 및 Equipment
- Corpse·Loot
- Action Control 생성
- 명시 번호 대상 선택
- 복합 Source 선택

#### 11.3 완료 기준

- 단일 표시 Snapshot의 Room B-1 번호 조회는 대상 수에 비례하지 않아야 함
- 반복되는 동일 Scope 조회 제거
- 새 N+1 SQL 패턴 없음
- 기존 SQL 조회 수와 변경 후 조회 수 기록
- 대표 처리 시간의 반복 측정 및 중앙값 비교
- 유의미한 응답 시간 증가가 있으면 원인 조사 및 해결
- 기준선보다 나빠진 항목은 승인된 예외 없이는 완료 처리하지 않음

측정 조건, 반복 횟수, 기준 SHA, 결과를 기록한다.

실제로 측정하지 않은 항목은 PASS로 처리하지 않는다.

기존 v1.3의 R01~R08은 본 설계에 모두 반영했다.
