# 프로젝트 공통 아키텍처 원칙

## 1. 목적과 적용 범위

이 문서는 원시구역의 프로젝트 공통 아키텍처 원칙의 유일한 규범 원문(SSOT)이다. Action, Combat, Actor, Item, Quest, Door, Web Client, Persistence와 개발 인프라의 새 기능·구조 변경·리뷰에 적용한다. [Issue #81](https://github.com/wonmin82/primal-zone/issues/81)에 따라 도입하며 특정 Actor 리팩터링의 구현 명세가 아니다.

각 원칙의 **필수 규범**은 지켜야 할 보장이고 **권장 방향**은 상황에 맞게 선택하는 방법이다. 예외는 적용 범위를 구별하는 것이며 보호할 불변식을 무시할 권한이 아니다. 중요한 정책 변경은 6절의 승인 절차를 따른다. 현재 코드 전체가 이 원칙을 이미 충족한다는 선언도 아니다.

## 2. 기본 설계 철학

1. 게임 경험과 데이터 안전성을 최우선으로 한다.
2. 하나의 도메인 사실에는 하나의 권위 있는 소유자를, 하나의 게임 효과에는 하나의 공식 규칙을 둔다.
3. 구성과 계약은 명시적으로 설계하되, 구현과 영속 상태는 필요한 최소 충분 수준으로 유지한다.
4. 기존 기능을 기본적으로 보존하면서 미래의 변경을 쉽게 만들고, 품질은 검증 가능한 근거로 입증한다.

**정적 계약은 명시적으로, 런타임 실행 경로는 단일하게, 영속 상태는 필요한 만큼만, 콘텐츠 구성은 선언적으로 설계한다.** 이 지향은 게임 경험과 데이터 안전성보다 상위에 있지 않다. 단순성은 클래스·코드 줄 수보다 중복 책임·암묵적 동작·불필요한 영속 상태·결합도를 줄이는 것이다. 확장성은 모든 미래 기능을 미리 구현하는 대신 이미 있는 기능을 새 콘텐츠에 조합할 때 공통 Parser·Gateway·Domain Service를 불필요하게 수정하지 않는 것이다.

## 3. 원칙별 상세 규범

<a id="p-01"></a>

### P-01 — Player-First Design

- **목적:** 사냥·장비 수집·성장을 중심으로 한 게임 경험과 제품 목표를 설계의 이유로 삼는다.
- **필수 규범:** 주요 임무와 보스의 기존 솔로 진행 가능성을 보존한다. 기술적 일관성이나 구조의 미관을 위해 실제 사용자 기능·조작 가능성·성장 동기를 희생하지 않는다.
- **권장 방향:** 변경 전후 플레이 흐름, 실패 안내, 웹 버튼과 직접 명령의 의미를 함께 검토한다. 탐험과 임무는 다음 사냥터와 성장 동기를 제공하도록 구성한다.
- **예외와 범위:** 승인된 제품 개선은 가능하지만 기능 삭제·게임 규칙 변경을 단순 리팩터링으로 처리하지 않는다. 사용자 편의도 권한·데이터 안전성의 우회를 정당화하지 않는다.
- **오해 방지:** 공동 전투 구조가 편하다는 이유로 주요 보스를 파티 필수로 바꾸지 않는다.
- **리뷰 질문:** 이 변경은 어떤 플레이 경험을 개선하는가? 혼자 하던 진행과 좁은 화면 조작이 유지되는가?
- **관련 규범:** [AGENTS.md](../AGENTS.md) 1·3절, [플레이 가이드](gameplay.md), [구조와 설계 결정](architecture.md).

<a id="p-02"></a>

### P-02 — Server Authority & Security

- **목적:** 신뢰 경계를 지키고 게임 결과·보상·권한·소유권의 최종 판단을 서버에 둔다.
- **필수 규범:** 클라이언트 입력·표시된 버튼·오래된 Target Reference·확인 토큰만으로 실행을 허용하지 않는다. 실행 시점의 Session 제어권, 대상의 현재 상태·위치·소유권과 필요한 권한을 서버에서 재검증한다. 인증정보를 게임·명령 기록에 노출하지 않는다.
- **권장 방향:** 입력을 명시적 계약으로 제한하고 실패는 비공개 정보를 노출하지 않는 사용법·오류로 안내한다.
- **예외와 범위:** AI·Timer는 사용자 Session을 가장하지 않고 신뢰된 서버 진입점을 사용할 수 있다. 이 경우에도 해당 도메인의 현재 상태·권한·효과 전제는 검증한다.
- **오해 방지:** 서명된 확인 토큰이나 서버가 과거에 표시한 버튼도 현재 실행 권한을 보장하지 않는다.
- **리뷰 질문:** 대상 이동·권한 소실·재접속 뒤 과거 요청이 오면 어떻게 거절하는가? 어느 경계에서 무엇을 신뢰하는가?
- **관련 규범:** [Action 아키텍처](action-architecture.md)의 선언과 실행 계약, [Issue #44](https://github.com/wonmin82/primal-zone/issues/44) D09·§8.

<a id="p-03"></a>

### P-03 — Correctness & Consistency

- **목적:** 실패·재전송·동시 실행에도 게임 상태와 자산의 의미를 보존한다.
- **필수 규범:** 하나의 도메인 변경은 일부만 반영되지 않도록 원자성을 보장한다. 멱등성은 별도 요구로, 같은 요청·서버 이벤트의 재실행이 효과·보상을 중복시키지 않게 한다. 실패 시 DB뿐 아니라 Evennia Cache와 예약 작업의 일관성도 복구한다. DB Commit과 네트워크 전달을 같은 원자적 작업으로 간주하지 않는다.
- **지연 작업의 확정 경계:** 게임 상태의 정확성에 필수적인 지연 작업은 재시작 후 실행 필요·완료 여부를 판정할 영속 근거를 도메인 상태 변경과 일관되게 확정해야 한다. 실행 예정 시각·상태 전이·안정적인 작업 또는 Encounter 식별자·완료 상태 등을 활용할 수 있으며 실제 저장 모델은 해당 도메인이 소유한다. `after_change()` 같은 메모리 콜백은 실행을 촉발할 수 있지만 재시작 복구가 필요한 작업의 유일한 상태 저장소가 되어서는 안 된다. DB Commit 성공 후 타이머 등록 콜백 실행 전에 서버가 종료되어도 확정된 도메인 상태로 후속 작업을 안전하게 복구할 수 있어야 한다.
- **권장 방향:** 도메인 변경 경계와 이벤트 정체성·완료 조건을 명시하고 외부 메시지·타이머 예약은 성공 Commit 뒤로 분리한다. 중첩 실패와 Commit 이후 전달 실패를 각각 검토한다.
- **예외와 범위:** 읽기 전용 계산마다 DB 트랜잭션을 요구하지 않는다. 의도한 다단계 작업은 각 단계의 확정·재시도·보상 또는 복구 경계를 별도로 정의한다.
- **오해 방지:** 트랜잭션 하나로 묶었다고 재요청 중복 지급이 방지되지는 않는다. 출력 실패를 이유로 이미 Commit된 보상을 재지급하지 않는다. 영속 작업의 실행 보장과 네트워크 메시지의 Exactly-Once Delivery는 별개이며, 복구·중복 호출에도 게임 효과·보상·전투 종료가 중복 확정되지 않아야 한다.
- **리뷰 질문:** 중간 실패 시 DB·Cache·예약이 함께 복구되는가? 동일 요청이나 종료 이벤트를 두 번 처리하면 어떤 상태가 남는가? Commit 직후 콜백이 누락되면 어떤 영속 근거로 후속 실행을 복구하는가?
- **관련 규범:** [Action 아키텍처](action-architecture.md)의 B-1 원자성·Rollback, [world_change()](../game/world/multiplayer.py), [전리품 권리](loot-claims.md).

<a id="p-04"></a>

### P-04 — Single Source of Truth

- **목적:** 같은 사실의 독립적 변경과 상충을 방지한다.
- **필수 규범:** 도메인 사실마다 권위 있는 소유자를 하나 정한다. Snapshot·Cache·읽기용 Projection에는 독립적 결정 권한을 주지 않고 원본과의 동기화·무효화·재구성 정책을 둔다.
- **권장 방향:** 모델 전체를 한 소유자에 몰기보다 사실별 소유권을 명시한다. 아이템 실물, 전리품 권리, 화폐 몫, 표시 번호의 책임을 구별한다.
- **예외와 범위:** 성능·화면·순수 규칙 계산을 위한 파생 데이터와 이력 보관은 허용한다. 쓰기용 delta를 계산하더라도 원본 도메인 경계에서 재검증·반영해야 한다.
- **오해 방지:** Inventory Cache를 허용한다는 말은 ItemEntity와 이중 저장·독립 수량 수정을 허용한다는 뜻이 아니다.
- **리뷰 질문:** 두 값이 다르면 무엇이 정답인가? 원본 변경·Rollback·재접속 뒤 파생 값을 어떻게 버리거나 다시 만드는가?
- **관련 규범:** [현재 runtime contract](architecture.md#현재-runtime-contract와-명시적-변환), [아이템 API](item-entities.md), [B-1 계약](action-architecture.md#b-1-물리-저장과-원자성).

<a id="p-05"></a>

### P-05 — Clear Responsibility & Dependency

- **목적:** 변경 이유가 다른 책임을 분리하고 의존성 방향을 일관되게 유지한다.
- **필수 규범:** 입력 해석, 실행 조정, 순수 게임 규칙, 영속화, 표현의 소유 책임을 구별한다. 순수 게임 규칙은 Evennia·DB·Web에 직접 의존하지 않는다. UI나 입력 어댑터가 별도 보상·권한 규칙을 소유하지 않는다.
- **권장 방향:** 어댑터와 실행 조정이 도메인 규칙·영속 API를 호출하고, 순수 규칙은 필요한 값과 결과만 다루게 한다. 실제 의존성 방향을 설명할 수 있어야 한다.
- **예외와 범위:** Evennia lifecycle·DB 잠금은 통합 계층의 정당한 책임이다. 작은 내부 함수마다 Repository Interface나 추상 계층을 추가할 필요는 없다.
- **오해 방지:** 책임 분리는 파일·클래스 수를 늘리거나 모든 함수를 순수 함수로 바꾸라는 요구가 아니다.
- **리뷰 질문:** 이 규칙을 웹 없이 검증할 수 있는가? 입력·표현 변경 때문에 경제·전투 규칙까지 바뀌는가?
- **관련 규범:** [AGENTS.md](../AGENTS.md) 3절의 계층별 역할, [rules.py](../game/world/rules.py), [Action 구성](action-architecture.md).

<a id="p-06"></a>

### P-06 — Single Authoritative Domain Execution

- **목적:** 하나의 게임 효과에 하나의 공식 규칙을 두어 진입점별 차이를 방지한다.
- **필수 규범:** 동일 효과를 여러 Handler에 독립 구현하거나 실패 시 Legacy Fallback으로 다시 실행하지 않는다. 사용자 명령·웹 Action·서버 Timer·AI는 같은 효과에 대해 공통 도메인 실행 규칙을 사용하고 불변식을 우회하지 않아야 한다.
- **권장 방향:** 진입점은 입력·호출 맥락을 조정하고 공통 Domain Service 또는 기존 도메인 API가 효과를 소유하게 한다.
- **예외와 범위:** 단일 Domain Execution은 하나의 Gateway나 하나의 입력 경로를 뜻하지 않는다. 사용자 Action의 공통 Gateway와 신뢰된 Timer 진입점은 공존할 수 있다. 별개 게임 효과까지 거대한 단일 Service로 합칠 필요도 없다.
- **오해 방지:** 서버 Timer를 사용자 Action Gateway에 무조건 통과시키거나, 반대로 Timer라는 이유로 별도 보상 공식을 복제하지 않는다.
- **리뷰 질문:** 같은 효과의 모든 진입점에서 실제로 호출하는 규칙은 무엇인가? 어댑터 실패 뒤 효과가 재실행되는 경로가 있는가?
- **관련 규범:** [Issue #44](https://github.com/wonmin82/primal-zone/issues/44) D09·D14, [Action 전환 경계](action-migration.md#전환과-데이터-경계).

<a id="p-07"></a>

### P-07 — Explicit & Verifiable Contracts

- **목적:** 공개 경계와 중요한 도메인 불변식을 명시하고 검증 가능하게 만든다.
- **필수 규범:** API 입력·결과·실패·완료 조건, 대상 선택, 권한, 상태 전이를 분명히 한다. 모호한 대상이나 유효하지 않은 상태를 임의 선택·조용한 Fallback으로 처리하지 않는다. 정적 선언의 오류와 실행 시점의 유효성은 각각 검증한다.
- **권장 방향:** 공개 계약은 타입·스키마·정적 검사·실행 경계 검사와 의미 있는 회귀 사례로 표현한다. Registered / Provided / Executable을 구별해 등록 사실만으로 제공·실행 가능성을 추정하지 않는다.
- **예외와 범위:** 일반 내부 순수 함수까지 Registry에 등록할 필요는 없다. 문서화된 Action별 기본 대상 정책은 모호한 후보의 임의 선택과 다르다.
- **오해 방지:** 정적 Registry 검증으로 현재 권한 검사를 대체하지 않는다. 명시한 대상이 실패하면 다른 대상으로 바꾸지 않는다.
- **리뷰 질문:** 잘못된 선언은 언제 실패하는가? 모호성·권한 거절·동기 완료 위반이 테스트 가능한 결과인가?
- **관련 규범:** [Action 아키텍처](action-architecture.md)의 등록·Role·Service 계약, [Issue #44](https://github.com/wonmin82/primal-zone/issues/44) D05·D06·D10·D11.

<a id="p-08"></a>

### P-08 — Declarative & Composable Content

- **목적:** 검증된 기능을 새 Actor·Item·Action 콘텐츠에 조합해 재사용한다.
- **필수 규범:** 조합형 콘텐츠의 구성·연결은 가능한 범위에서 선언적으로 표현한다. 기존 기능을 재조합할 때 공통 Parser·중앙 Dispatcher에 콘텐츠 종류별 조건문을 불필요하게 추가하지 않는다.
- **권장 방향:** 콘텐츠가 제공 기능·역할·설정을 선언하고 재사용 가능한 Service가 효과를 실행하도록 한다. 정적 연결은 등록 시 검증한다.
- **예외와 범위:** 새 문법 종류는 공통 Grammar 확장이 필요할 수 있고, 새로운 게임 알고리즘은 코드로 구현할 수 있다. 모든 로직을 범용 DSL로 바꾸지 않는다.
- **오해 방지:** 선언형이라는 이유로 임의 Python 실행이나 무제한 런타임 등록을 허용하지 않는다. 현재 Action Manifest의 명시적 등록 정책은 유지한다.
- **리뷰 질문:** 같은 기능을 가진 새 콘텐츠를 어디에 선언하면 되는가? 공통 코드 수정은 새 의미·문법에 필요한가, 단지 새 종류 이름 때문인가?
- **관련 규범:** [Action Manifest와 Service](action-architecture.md), [Issue #44](https://github.com/wonmin82/primal-zone/issues/44) §2.

<a id="p-09"></a>

### P-09 — Minimal Sufficient Design

- **목적:** 현재 요구와 검증된 변경 가능성을 충족하는 최소 충분 구조를 선택한다.
- **필수 규범:** 새 Registry·Adapter·영속 모델·범용 프레임워크에는 독립 책임과 검증 가능한 필요성이 있어야 한다. 단순화를 위해 원자성·명시적 계약·복구에 필요한 상태를 제거하지 않는다.
- **권장 방향:** 기존 도메인 API 재사용, 계산 가능한 파생 값, 필요한 식별·완료 기록을 구별한다. 새 구조 없이 해결하는 대안과 확장 비용을 함께 비교한다.
- **예외와 범위:** 권한·멱등성·재시작 복구를 위해 구조나 저장 상태가 늘어나는 것은 정당하다. 미래 가능성만으로 모든 모드를 지원하는 엔진을 선제 구축하지 않는다.
- **오해 방지:** 클래스 수나 DB 행 수가 적다고 항상 단순한 설계는 아니다. 의미 없는 영속 Snapshot과 복구에 필수인 완료 기록은 다르다.
- **리뷰 질문:** 이 추상화나 상태를 제거하면 어떤 요구가 깨지는가? 기존 구조 재사용이 어려운 근거와 유지 비용은 무엇인가?
- **관련 규범:** [AGENTS.md](../AGENTS.md) 2·3절, [현재 저장 책임](architecture.md), [Issue #44](https://github.com/wonmin82/primal-zone/issues/44) D13.

<a id="p-10"></a>

### P-10 — Stable Identity & Controlled Evolution

- **목적:** 재접속·표시 변경·콘텐츠 진화에도 영속 정체성과 공개 계약을 관리한다.
- **필수 규범:** 영속 ID를 표시 이름·정렬·가시성과 구별한다. 공개 행동 계약·영속 구조 변경에는 영향·호환성·이전·복구·검증 방법을 명시한다. 기존 호환성 보존을 기본으로 하되 승인된 개선과 보안·무결성 결함 수정을 금지하지 않는다.
- **권장 방향:** 안정 ID와 명시적 변환을 사용하고 새 데이터뿐 아니라 기존 데이터의 로드·기본값·재접속도 검토한다.
- **예외와 범위:** 표시 번호의 이동·해제·리셋은 해당 도메인의 승인된 정책을 따른다. B-1을 모든 객체·목록의 보편 식별 정책으로 확대하지 않는다.
- **오해 방지:** B-1은 배열 인덱스·UUID·수량이 아니다. 시야나 권한 변화로 재번호하지 않으며 결번 비재사용과 그룹 전체 소멸 시 리셋의 범위는 기존 계약을 따른다.
- **리뷰 질문:** 이름·위치·접속 상태가 바뀌면 어떤 정체성을 유지하는가? 기존 참조와 데이터의 변환 실패를 어떻게 복구하는가?
- **관련 규범:** [Issue #44](https://github.com/wonmin82/primal-zone/issues/44) D15~D17·§4.2, [B-1 저장 계약](action-architecture.md#b-1-물리-저장과-원자성), [아이템 migration](item-migration.md).

<a id="p-11"></a>

### P-11 — Recoverability & Operability

- **목적:** 장애·재시작 뒤 안전하게 복구하고 원인을 진단할 수 있게 한다.
- **필수 규범:** 새 빈 DB, 중단된 초기화, 지원하지 않는 과거 DB, 손상된 기존 DB, 불완전한 상태를 구별한다. 복구 불가능한 상태를 정상으로 간주하지 않는다. 운영 데이터의 무단 삭제·암묵적 변환을 금지하고 원인 진단이 가능한 오류를 제공한다.
- **재시작 정합화:** 서버 시작 또는 도메인 재활성화 시 P-03의 영속 근거를 이용해 실행이 필요한 미완료 작업, 이미 완료된 작업, 실행 예정 시각이 지난 작업, 중복 등록·호출된 작업, 현재 상태에서 무효화된 작업을 구별해야 한다. 복구·재예약·실행·생략은 기존 게임 규칙과 도메인 정책을 따르고 동일 작업의 중복 호출에도 효과·보상·종료를 한 번만 확정한다. Commit 이후 메모리 콜백이 누락된 경우도 이 판정으로 복구하며 완료된 작업을 다시 확정하지 않는다.
- **권장 방향:** 반복 가능한 초기화·검증·재시작 reconciliation, 명시적 백업·변환·복원 절차를 마련한다. 오류는 필요한 진단 맥락을 보존하되 비밀·인증정보를 노출하지 않는다.
- **예외와 범위:** 승인된 maintenance 변환·복원은 가능하다. Fresh 설치 정책은 과거 DB 자동 변환이나 손상 DB를 빈 DB로 재해석할 권한이 아니다. Combat·Respawn·Recovery 등 기존 도메인의 영속 상태와 실행 계약을 활용할 수 있으며 범용 Scheduler·Event Bus·Message Queue·새 영속 작업 테이블을 요구하지 않는다. 이 규범은 개별 도메인의 복구 구현이 이미 완료되었다는 선언이 아니다.
- **오해 방지:** marker가 없다는 이유만으로 진행 기록을 초기화하거나, 실패를 숨겨 성공으로 시작하지 않는다.
- **리뷰 질문:** 어느 상태에서 재시작·재시도가 안전한가? 예정 시각 경과·완료·중복·무효화 작업을 어떻게 판정하는가? 운영자 승인 없이 바뀌는 데이터가 있는가? 실패 원인과 복구 경로를 구별할 수 있는가?
- **관련 규범:** [설치와 legacy upgrade](installation.md#fresh-installation과-legacy-upgrade), [아이템 migration](item-migration.md), [Door 복구 경계](doors-and-keys.md).

<a id="p-12"></a>

### P-12 — Evidence-Driven Quality

- **목적:** 설계 품질과 동작 보장을 실제 검증·측정 근거로 판단한다.
- **필수 규범:** 테스트·실제 실행·CI·독립 리뷰의 근거와 보장 범위를 구별한다. SHA·환경·미커밋 변경 범위·실행 여부를 식별하고 미실행을 PASS로 보고하지 않는다. 가능한 한 성능 최적화·대규모 구조 변경은 실제 측정과 영향 분석에 근거한다.
- **권장 방향:** 중요한 경계·실패·재접속·중복 효과를 검증하고 최적화 전후의 의미와 비용을 비교한다. 측정이 불가능하면 가설·근거·검증 공백을 명시한다.
- **예외와 범위:** 문서·작은 변경에 무조건 전체 게임 검사를 요구하지 않는다. 검사 선택·기존 성공 재사용·비동기 감시·CI 확인의 상세 정책은 AGENTS.md를 따른다.
- **오해 방지:** Mock·자동 브라우저·리뷰 성공을 실제 OS IME·운영 복원·다른 플랫폼 성공으로 확대하지 않는다.
- **리뷰 질문:** 이 주장의 실제 증거와 기준 코드는 무엇인가? 미검증·실패·추정과 재사용한 과거 결과가 구별되는가?
- **관련 규범:** [AGENTS.md](../AGENTS.md) 4절, [테스트 안내](playtest.md), [비동기 감시기](codex-watch.md).

## 4. 원칙 위계와 충돌 해결

설계의 목적은 P-01과 제품 목표다. 안전·도메인 불변식은 P-02·P-03·P-04·P-07·P-10·P-11로 보호하고, P-05·P-06·P-08·P-09의 구조적 품질을 그 경계 안에서 최적화한다. P-12는 선택의 보장 범위를 입증한다. 이 분류는 낮은 분류의 필수 규범을 생략하거나 게임 편의를 위해 안전성을 희생하는 순위표가 아니다.

1. 관련 도메인의 불변식을 먼저 확인한다.
2. 충돌하는 P-ID, 기존 승인된 설계 결정과 적용 범위를 찾는다.
3. 양쪽을 만족하는 대안을 우선 검토한다.
4. 불가피하게 희생할 요소와 잃는 보장·영향 대상을 기록한다.
5. 데이터·권한·게임 동작·성능·복구·이전 및 검증 영향을 평가한다.
6. 중요한 정책 변경은 별도 명시적 승인 후 반영한다.

파일 경로나 문서 작성 시점만으로 권위 관계를 정하지 않는다. 적용 범위·명시적 결정·승인 이력을 함께 확인한다. 이 문서는 [Issue #44](https://github.com/wonmin82/primal-zone/issues/44) 등 구체적 Design Freeze를 자동 무효화하지 않는다. 충돌은 A(문구·해석 명확화), B(도메인별 적용 범위 구별), C(실제 설계 변경·승인 필요)로 분류한다. A/B는 기존 의미를 보존하며 설명하고, C는 기존 근거·대안·후속 처리 방안을 PR에 보고한 뒤 승인 전 변경을 보류한다.

## 5. 불변식과 최적화할 품질 속성

| 구분 | 보호·판단 기준 |
| --- | --- |
| 보호할 불변식 | 서버 권위, 권한·소유권, 사용자 데이터·보안, 상태·보상·자산 일관성, 영속 정체성, 장애·재시작 복구성, 무단 데이터 변경 방지 |
| 균형 있게 최적화할 속성 | 단순성, 재사용성, 확장성, 성능, 유지보수성, 추상화 수준, 코드 중복 최소화 |

코드량·처리 속도 개선과 데이터 손실·중복 보상을 동등한 비용으로 비교하지 않는다. 불변식을 보존하는 대안 안에서 품질 속성의 비용을 비교한다. 불변식 자체의 계약 변경은 일반 최적화가 아니라 영향·복구·명시적 승인을 요구하는 정책 변경이다.

## 6. 아키텍처 결정과 예외 승인

기존 계약 안의 구현 선택은 작업 범위에 맞게 결정하고 변경 PR에 근거를 남긴다. 새 추상화·Registry·Adapter·영속 모델은 독립 책임·소유권·필요성·기존 구조 재사용 대안을 설명한다. 사소한 변경에 별도 ADR이나 승인 단계를 강제하지 않는다.

공개 계약, 게임 규칙, 권한·데이터 안전, 영속 ID, 승인된 Design Freeze를 바꾸거나 원칙의 필수 규범에 예외가 필요하면 변경 전에 별도 설계 Issue 또는 범위가 명확한 변경안으로 명시적 사용자 승인을 받는다. 요청된 작업에 그 변경의 명시적 승인이 이미 포함되면 동일 승인을 반복 요청하지 않는다. 보안·무결성 오류도 호환성을 이유로 영구 유지하지 않되 승인·검증된 수정으로 처리한다.

결정 기록에는 문제·관련 P-ID·현재 계약과 근거·대안·선택 이유·포기하는 보장·영향·이전/복구·검증·승인 근거를 필요한 만큼 포함한다. 예외에는 적용 범위·책임자·유효 조건과 재검토 또는 종료 조건을 덧붙인다. 승인 후 관련 도메인 규범과 구현·검증 근거를 함께 갱신한다. 구현 착수·Commit/Push·PR Merge·Issue 종료·브랜치 삭제의 권한은 [AGENTS.md](../AGENTS.md)를 따르며 설계 승인에서 자동 파생하지 않는다.

## 7. 설계와 코드 리뷰 적용

변경에 영향받는 P-ID와 불변식만 선택한다. 작은 문구 수정마다 12개 원칙의 형식적 전체 체크리스트를 작성하지 않는다. Action·Actor·Item은 조합과 소유권, Quest·Combat은 종료·보상·중복 이벤트, Door는 현재 권한·시간 경계·재시작, Web은 Session·오래된 참조·표현과 실행 분리, 인프라는 데이터 보존·안전 실패를 중심으로 질문한다.

리뷰는 실제 Diff·소스·도메인 규범·검증 근거에서 판단한다. 여러 진입점의 효과 중복, 이중 SSOT, 의미 없는 영속 Snapshot, 묵시적 Legacy Fallback, 신규 구조의 불분명한 책임을 확인한다. 지적에는 발생 조건·영향·근거·수정 방향을 남기고 확인된 결함과 추정·미검증을 구별한다. 검사와 독립 리뷰의 역할·운영 방법은 AGENTS.md를 따른다.

## 9. 설계 판단 사례

각 사례의 **일반 판단**은 프로젝트에 적용할 기준이고, **구현 참고**는 관련 도메인 문서·소스가 소유하는 비규범적 설명이다. 구체적 구현 상태와 확인 기준은 해당 변경 PR의 검증 기록을 확인한다. **향후 예시**는 구현 완료나 승인된 세부 설계를 뜻하지 않는다. 사례 검토 자체도 실제 게임 테스트 성공을 뜻하지 않는다.

### ItemEntity와 Inventory Cache

**일반 판단:** P-04/P-05/P-09에 따라 ItemEntity SSOT를 유지하며 파생 Inventory Cache는 허용하되 실물 변경은 원본 API에서 검증·반영하고 무효화·Rollback을 보장한다. Cache를 없애기 위해 순수 규칙을 DB에 결합하거나 Cache를 독립 원장으로 저장하는 선택은 피한다. **구현 참고:** Native ItemEntity와 EquipmentProfile의 일시적 수량 계산 context는 [architecture.md](architecture.md)와 [item_inventory.py](../game/world/item_inventory.py)를 참조한다.

### 사용자 Action Gateway와 서버 Combat Timer

**일반 판단:** P-02/P-03/P-06에 따라 사용자 Action Gateway와 서버 Timer의 진입점은 달라도 같은 효과의 규칙·비용·보상·완료 계약을 공유해야 한다. **구현 참고:** 사용자 공통 Gateway 계약은 [Action 문서](action-architecture.md), 전투 실행·시간 경계는 [enemies.py](../game/typeclasses/enemies.py)·[explorers.py](../game/typeclasses/explorers.py)를 참조한다. **향후 예시:** 공통 Combat Domain Service로 조정하더라도 Timer를 사용자 Session 요청으로 위장할 필요는 없다. 이 예시는 모든 전투의 Gateway 통합 완료를 주장하지 않는다.

### Shared Encounter와 Exclusive Duel

**일반 판단:** P-03/P-06/P-09/P-11에 따라 종료 전이·중복 종료 방지·보상 1회 계약은 공통으로 지킨다. 참여·복구 요구가 다르면 저장 모델을 구별할 수 있다. 모든 모드에 같은 영속 Snapshot을 강제하거나, 최소 저장을 이유로 식별·완료·재시작 복구에 필요한 상태를 없애지 않는다. **구현 참고:** 공유 적의 HP·점유·참여 보상은 [공유 전투 문서](architecture.md)를 참조한다. **향후 예시:** Exclusive Duel과 Shared Encounter의 저장 모델 비교는 Actor 통합·대련 구현 완료 주장이 아니며 구체적 모델은 별도 설계·승인·검증 대상이다.

### Fresh DB 초기화와 손상된 기존 DB

**일반 판단:** P-03/P-09/P-10/P-11에 따라 최소 marker를 쓰더라도 marker 누락만으로 기존 DB를 Fresh로 판정하지 않는다. 기존 데이터·불완전한 관계·손상을 확인하면 안전하게 실패하고 진단·백업·승인된 복구로 연결한다. **구현 참고:** 빈 world의 native 초기화와 기존 데이터 migration 경계는 [설치 안내](installation.md)·[item_runtime.initialize_fresh()](../game/world/item_runtime.py)를 참조한다. 이 참조는 함수 하나가 모든 DB 손상·초기화 중단을 진단한다는 보장이나 새 자동 복구 기능의 구현 완료 선언이 아니다.

## 10. 원칙 자체의 변경 관리

P-ID는 참조 정체성이므로 조용히 재번호하거나 다른 의미로 재사용하지 않는다. 오탈자·설명 명확화와 규범 의미 변경을 구별한다. 의미 변경은 이유·관련 도메인과 승인 이력·호환성·불변식·대안·검증 영향을 명시한 별도 변경안으로 검토·승인하고 이 원문을 갱신한다. 폐기·대체 시 이전 ID와 대체 관계를 남긴다. 개별 Issue의 임시 제안을 자동으로 공통 규범으로 승격하지 않는다.

AGENTS.md·README·도메인 문서는 이 원문을 링크하고 각자 소유한 계약만 유지한다. 원칙 변경으로 기존 Design Freeze에 영향이 있으면 4·6절의 충돌·승인 절차를 거쳐 해당 도메인 결정도 명시적으로 갱신한다.
